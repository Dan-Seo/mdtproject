# PROGRAM — 조작 지연 최적화 루프

`PROGRAM.md`(Lighthouse 루프)의 후속. 저쪽은 "처음 열 때"를 재고 이쪽은 "쓰는 동안"을 잰다.
desktop Lighthouse는 이미 만점이라 기울기가 없었지만, 조작 비용은 도면 규모에 따라 커진다 —
이 도구의 실제 부담은 여기다.

## 목적함수

**`pitchEdit`의 net task ms** (`scripts/perf/interaction.mjs`, 8×8 스팬, 워밍업 3회 후 9회 중앙값).
帯筋 피치를 한 칸 고쳤을 때 메인스레드가 태우는 전체 시간이다.

> **2026-08-11 변경 (사용자 승인).** 원래 목적함수는 net **script** ms였다. 1차 루프가
> 그 값을 26.1 → 9.1ms로 줄이고 나니 Script가 실제 비용의 36%에 불과해졌다 —
> Layout 7.5ms는 루프 내내 한 번도 보이지 않았다(2차 검토 참조). `TaskDuration`은
> Script·Layout·Style·페인트를 모두 포함하므로 사용자가 기다리는 시간에 더 가깝다.
> `netScriptMs`도 저널에 계속 남긴다 — 회귀 진단에 필요하다.

측정은 벽시계가 아니라 **CDP Performance의 `ScriptDuration`**을 쓴다. 벽시계로 재면 값이
프레임(16.7ms) 배수에 붙어버려, 규모를 6배로 키웠는데 더 빨라지는 무의미한 수가 나온다.

### 베이스라인 (2026-08-11, 8×8 스팬 = 平面 부재 225)

net script ms 기준 — 1차 루프 시점:

| 시나리오 | 측정 1 | 측정 2 | 흔들림 |
| --- | --- | --- | --- |
| idle (유휴 2프레임) | 0.7 | 0.9 | 0.2 |
| **pitchEdit** | **26.1** | **25.8** | **0.3** |
| memberClick | 1.8 | 1.8 | 0 |
| viewerTab | 4.9 | 5.2 | 0.3 |

**NOISE = 1ms.** 26ms 값에 흔들림이 0.3ms다. Lighthouse 점수(±4점)와는 신호 대 잡음비가
다르다 — 그래서 이 목적함수를 쓴다.

net task ms 기준 베이스라인은 2차 루프에서 새로 잡는다. Task는 Script보다 흔들림이
크므로(페인트가 섞인다) 판정 문턱도 그에 맞춘다.

Lighthouse 루프의 "빌드·로딩 계층만" 제한은 여기 적용되지 않는다. 조작 지연은 런타임

## 프로파일이 확정한 사실 (2026-08-11)

`pitchEdit` 26ms의 내역 — CDP Profiler, 50µs 샘플링, 편집 25회:

```
17.25 ms  (program)            ← V8의 네이티브/드라이버 버킷
14.17 ms  getProgramInfoLog    ← 셰이더 링크 완료를 기다리는 동기 스톨
 0.86 ms  getShaderInfoLog
 0.65 ms  shaderSource
 0.44 ms  getProgramParameter
 이하 전부 0.7ms 미만 (React 재렌더, 225개 SVG, 지오메트리 재구축 포함)
```

**편집 1회마다 셰이더 프로그램을 새로 컴파일·링크한다.** 원인은 `disposeContent`가
`contentMaterials`를 매번 폐기하고(`Viewer3D.tsx:114`) `rebuildMemberScene`이 새
`MeshStandardMaterial`을 만드는 것(`Viewer3D.tsx:466,471`). 머티리얼을 폐기하면 그 WebGL
프로그램이 해제되므로 다음 렌더에서 처음부터 다시 링크한다.

React 재렌더·SVG·지오메트리는 **범인이 아니다.** 여기를 최적화하지 말 것.

> 이전 루프에서 `checkShaderErrors = false`는 "콜드 캐시에서만 보이는 신기루"로 기각됐다.
> 그 판단은 *페이지 로드* TBT 기준으로는 옳았다. 편집 경로는 상황이 다르다 —
> 목적함수가 바뀌면 기각됐던 후보를 다시 볼 것.

## 1차 루프 결과 (2026-08-11)

**`pitchEdit` 26.1ms → 9.1ms (−65%).** 3라운드, 채택 1건.

### 채택 — 머티리얼을 마운트 수명으로 풀링

`Viewer3D.tsx`. `disposeContent`가 재구축마다 머티리얼을 폐기하고 rebuild가 새로 만들던 것을
`materialPool`(마운트 수명, 언마운트에서만 폐기)로 바꿨다. 계측으로 확인한 효과:

```
断面 편집 1회당 GL 호출     이전    이후
  linkProgram                5       0
  compileShader             10       0
  deleteProgram              5       0
```

**단, 部材 뷰(일반 `Mesh`)와 建物 뷰(`InstancedMesh`)는 파라미터가 같아도 풀 항목을 나눠야
한다.** 하나로 공유했더니 `USE_INSTANCING` 정의가 다른 프로그램 사이를 오가며
`viewerTab`이 5.3 → 11ms로 퇴행했다. `rebar` / `buildingRebar`로 분리해 해결.

실브라우저 확인: 部材·建物 양쪽 렌더 정상, 편집이 3D·内訳書에 정확히 반영
(피치 100→250 → 帯筋 本数 36→15, 総延長 984.960→410.400). desktop Lighthouse 100 유지.

### 기각

| 후보 | 결과 | 이유 |
| --- | --- | --- |
| `renderer.debug.checkShaderErrors = false` | 게이트 실패 + 25.8→28.3ms | `WebGLRendererMock`에 `debug`가 없어 12개 실패. 성능도 악화 — 스톨이 `getProgramParameter(LINK_STATUS)`로 옮겨갈 뿐 드라이버 링크 자체는 남는다 |

### 남은 것

- `viewerTab`이 5.4 / 5.5 / **7.1**로 가끔 튄다. 중앙값은 가드 안이지만 베이스라인
  (4.9 / 5.2 / 5.3)보다 분산이 크다. 프로그램 분리가 완전하지 않을 수 있다.
- **유휴 CPU**: 3D가 변화 없는 장면을 매 프레임 다시 그린다. 8×8 규모에서 유휴 2프레임에

  render-on-demand 후보 — 단 오토로테이트·트윈은 보이는 움직임이므로 그동안은 계속 그려야 한다.

## 2차 검토 — 목적함수의 사각지대 (2026-08-11)

1차 루프가 끝난 상태에서 "이게 최적해인가"를 확인하려고 편집 1회를 완전 분해했다.
**결론: 아니다. 목적함수가 실제 비용의 36%만 재고 있었다.**

### 편집 1회의 실제 메인스레드 시간 (8×8, 부재 225, DOM 1304노드)

| | 베이스라인 | 1차 루프 후 |
| --- | --- | --- |
| **TaskDuration** | **41.3** | **25.0** |
| ├ ScriptDuration | 26.1 | 9.1 ← 루프가 최적화한 유일한 항목 |
| ├ LayoutDuration | 7.4 | **7.5 ← 미동도 없음** |
| ├ RecalcStyleDuration | 0.2 | 0.2 |
| └ 나머지(페인트·컴포짓) | 7.6 | 8.2 |

### 확정된 사실 — 재조사 불필요

- **1차 채택분은 그 축에서 완결됐다.** 편집당 GL 호출 `linkProgram`·`compileShader`·
  `deleteProgram`·`createProgram`·`texImage2D` 모두 **0회**. 더 짜낼 것이 없다.
- **남은 Script는 SwiftShader 아티팩트가 아니다.** 캔버스 픽셀을 366,085 → 2,936으로
  125배 줄여도 편집 비용은 8.1 → 7.7ms로 불변. 실기기 GPU로 바꿔도 사라지지 않는다.
- **Layout은 문서 전체에 걸린다.** `Layout ≈ 1.1 + 0.0048 × DOM노드`
  (463노드 3.3ms → 1304노드 7.3ms). 반면 `memberClick`은 규모와 무관하게 0.1ms.
- **편집 1회가 DOM 속성을 128건 쓴다.** 그중 실제 내용 변경은 数量内訳書의
  characterData 9.2건 + childList 4건뿐. 나머지 114건은 React가 바뀌지도 않은
  `<input>`의 `name`(80건)·`type`(34건)을 재기록하는 것 — 平面エディタ 페인 48건 포함.
- **비용을 만드는 것은 `type`이다.** input 40개에 `name` 재기록 → Layout **0ms**(공짜),
  `type` 재기록 → Layout **10.6ms**. 数量 숫자 텍스트 교체만 해도 Layout **5.6ms**.

### 주범 — 平面 SVG의 레이아웃 세금

`平面エディタ` 페인만 골라 개입한 결과:

| 개입 | Script | Layout | Task |
| --- | --- | --- | --- |
| 통제군 | 8.4 | 7.2 | 23.3 |
| `visibility: hidden` (레이아웃은 수행됨) | 7.1 | 7.0 | 18.9 |
| 부재 1/3 숨김 (225 → 153 렌더) | 7.5 | 7.4 | 21.3 |
| `display: none` (레이아웃에서 제외) | 6.2 | **0.6** | **9.0** |

`visibility:hidden`은 비용을 유지하고 `display:none`은 없앤다 → **레이아웃이 맞다.**
부재 수를 줄여도 안 줄어든다 → **부재 개수가 아니라 SVG 서브트리 재계산 자체가 비용이다.**

그리고 **편집 시 平面 SVG의 DOM은 단 한 건도 변경되지 않는다.** 순전히 다른 페인의
변경에 끌려 853노드(`<line>` 288, `<text>` 259, `<g>` 225, `<rect>` 81)가 통째로 재계산된다.

원인은 `PlanEditor.module.css`의 `.drawing { width: 100%; height: 100% }` —
퍼센트 크기라 SVG 루트의 레이아웃이 컨테이너에 종속되고, 그리드 어디가 더러워지든
따라서 다시 계산된다. `contain: layout`(페인)·`contain: strict`(svg)·
`content-visibility: auto`는 **전부 듣지 않았다.**

### 처방 후보 — CSS만 주입해 검증 (소스 미수정)

| 처방 | Script | Layout | Task |
| --- | --- | --- | --- |
| 통제군 | 8.4 | 7.6 | 23.1 |
| SVG `<text>` 숨김 (진단용) | 6.6 | 3.2 | 14.2 |
| **SVG 고정 px 크기만** | 7.1 | **0.5** | **10.6** |
| SVG `position: absolute`만 | 7.0 | 0.8 | 11.0 |
| 고정 px + `contain: strict` | 5.9 | **0.5** | **8.3** |

두 요인이 독립적으로 듣는다. **고정 px 크기 하나만으로 Task 23.1 → 10.6ms.**
`<text>` 259개가 레이아웃 비용의 절반이다(폰트 계측).

## 2차 루프 결과 (2026-08-11) — 3라운드, 채택 0건

목적함수를 `netTaskMs`로 바꾸고 平面 SVG의 레이아웃 세금을 공략했다. **세 후보가 모두
"보이는 레이아웃 불변" 가드에 걸려 되돌아갔다.** 성능은 셋 다 실제로 좋아졌다 — 문제는 값이다.

### 새 베이스라인 (netTask ms, 8×8)

| 시나리오 | 측정 1 | 측정 2 |
| --- | --- | --- |
| **pitchEdit** | **25.0** | **23.9** |
| memberClick | 2.3 | 2.6 |
| viewerTab | 5.7 | 8.5 |
| idle (Task 절대값) | 1.8 | 1.9 |

**NOISE ≈ 1.1ms** (Script의 0.3ms보다 크다 — 페인트가 섞인다). `viewerTab`은 여전히 요동친다.

### 기각

| 후보 | 성능 | 기각 사유 |
| --- | --- | --- |
| **IB1** `.drawing { position: absolute }` | netTask **17.2** (−6.7), Layout 7.6→4.0 | 900×600에서 平面 높이 257 → **220px**. 흐름에서 빠지면서 `viewBox` 종횡비의 높이 기여가 사라진다 |
| **IB2** ResizeObserver로 잰 px 크기 | (측정 전 기각) | **경로 의존 되먹임.** SVG에 px 높이를 박으면 그 값이 다시 프레임 높이를 정해 잠긴다. 1600에서 900으로 줄여도 484px에 고정 |
| **IB3** IB1 + 프레임 `aspect-ratio` | (측정 전 기각) | `aspect-ratio`가 그리드가 늘려준 높이까지 덮는다. 1600×1000에서 484 → **357px**, 1280×800에서 334 → **286px** |

### 왜 셋 다 실패했는가

현재 크기 계약은 **"그리드 행 높이가 확정이면 채우고(1600에서 484px), 미확정이면 `viewBox`
종횡비로 떨어진다(900에서 257px)"** 이다. 이것이 정확히 흐름 안의 SVG에 걸린 `height: 100%`가
하는 일이고, **퍼센트 없이는 CSS로 재현할 수 없다.** 그리고 그 퍼센트가 곧 레이아웃 종속의
원인이다. 즉 세금과 반응형 동작이 같은 한 줄에서 나온다.

`contain: layout` / `contain: strict` / `content-visibility: auto`는 앞서 전부 무효로 확인됐다.

### 남은 선택지 — 전부 사람의 결정이 필요하다

1. **크기 계약을 바꾼다.** 平面 영역 높이를 내용과 무관하게 고정한다. 좁은 뷰포트에서
   도면이 어떻게 보여야 하는지가 UX 결정이라 임의로 정할 수 없다. 정해지면 −13ms 수준.
2. **재레이아웃 비용 자체를 줄인다.** `<text>` 259개가 레이아웃의 절반이다
   (숨기면 7.3 → 3.2ms). 부재 라벨을 스팬 수가 많을 때 생략하는 식 — 역시 UX 결정.
3. **M4까지 보류한다.** 지금 규모(8×8)에서 편집 25ms는 체감 한계에 가깝다. 세금은
   DOM 노드 수에 선형이므로 다층·다스팬(R4)이 실제로 들어올 때 다시 본다.

### 재조사 불필요

- `position: absolute` 계열은 좁은 뷰포트 높이를 반드시 깨뜨린다. 종횡비로 보정하려 하면
  넓은 뷰포트를 깨뜨린다. 이 두 실패는 같은 원인의 양면이다.
- ResizeObserver로 잰 px를 SVG에 박는 방식은 **되먹임 때문에 근본적으로 불안정하다.**
  프레임 높이가 SVG 내용에 의존하는 한 측정값이 자기 자신을 결정한다.

   `interaction.mjs`는 이미 네 지표를 전부 저널에 적고 있으므로 하네스 수정은 불필요하다.
   **단 이 변경은 평가 기준 변경이므로 사용자 승인 없이 적용하지 않는다.**
2. 그 다음 후보는 平面 SVG에 컨테이너를 ResizeObserver로 재어 **명시적 px 크기**를 주는 것
   (`Viewer3D`가 캔버스에 이미 쓰는 패턴). 반응형은 유지된다. 예상 −12ms Task.
3. `type` 재기록을 없애는 메모이제이션은 **후순위다.** 필요 변경(数量 텍스트)만으로도
   Layout 5.6ms가 나오므로, SVG를 먼저 고치지 않으면 효과가 겹쳐 묻힌다.
