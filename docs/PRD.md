# PRD: 일본 RC 배근상세·물량산출 시스템

## 목표

일본 종합건설사(제네콘) 공무부가 구조도에서 읽은 **설계 배근정보를 바꾸지 않고**, 배근상세와
철근·콘크리트·거푸집 물량을 산정하되 **모든 숫자를 원본 입력과 규정 조항까지 역추적**할 수 있게 한다.

빌더허브(창소프트)의 일본판이다. 핵심 자산은 3D 엔진이 아니라 **기준에 묶인 룰셋**이고,
일본판은 그 룰셋을 일본 기준과 일본 현장 관행으로 교체하는 작업이다.

### 이 제품이 "자동 배근"이라고 부르는 것

구조해석·구조설계를 하지 않는다. 사용자가 입력한 주근 직경·본수, 후프/스터럽 직경·간격·구간을
**그대로 사용**하고 다음만 자동 산정한다.

- 피복 적용과 건축기준법 시행령 제79조 피복 하한검증
- 정착·이음의 방식, 위치 가정, 길이
- 입력된 후프/스터럽 규격·간격에 따른 형상·길이·본수
- 부재별 철근 설계수량·소요수량

필요 주근량, 직경, 본수, 전단보강근 간격을 구조적으로 결정하지 **않는다.**

## 사용자

| 페르소나 | 하는 일 | 지금의 고통 | 우리가 주는 것 |
|---|---|---|---|
| **현장 공무 담당자** (주 사용자) | 실행예산 편성, 철근 하도급 발주량 산정 | 엑셀 + 경험. 도면이 바뀌면 처음부터 다시 | 배근정보를 넣으면 직경별 설계·소요중량이 근거와 함께 나옴 |
| **현장소장 / 공사부장** | 숫자 승인, 발주처 설명 | 부하가 준 숫자의 근거를 자기가 못 만듦 | 입력부터 조항·공식·반올림까지 계산 경로를 열어볼 수 있음 |
| **정보시스템부** (도입 게이트키퍼) | 소프트웨어 도입 심사 | 클라우드로 도면이 나가는 걸 승인할 수 없음 | 앱이 자동으로 내보내는 것이 **아예 없음**을 테스트로 증명 |
| 본사 기술/적산 관리부 | 사내 기준 통제, 현장 물량 파악 | 현장마다 계산 방식이 제각각 | 파일럿은 담당자가 보낸 엑셀로 확인 (웹 집계는 v1.1) |
| 본사 견적 담당 | 입찰 단계 개산 물량 | 정밀 산출은 시간이 오래 걸림 | v1.1 |

## 핵심 기능 (MVP)

| ID | 기능 |
|---|---|
| UC-1 | 설계 배근정보를 변경하지 않고 배근상세·물량 산출 |
| UC-2 | 직경별·강종별 철근 설계수량과 소요수량 산출 (躯体 4% 할증) |
| UC-3 | 산출값을 원본 입력·공식·반올림·조항까지 역추적 (계산 DAG) |
| UC-4 | 설계 피복값에 대한 시행령 제79조 제1항 하한 위반 검출 |
| UC-5 | 구조도만 있을 때 배치·단면일람표·배근표·슬래브/벽 형상 직접 입력 |
| UC-6 | `VALID` 물량표 엑셀 + 감사 JSON 내보내기 |
| UC-9 | 앱이 어떤 외부 네트워크 요청도 하지 않음을 증명 |
| UC-10 | 자동저장 + 버전이 붙은 프로젝트 JSON 저장/불러오기 |

조건부 — 가설 확인 후 착수: **UC-7** 사내기준 덮어쓰기(H6), **UC-11** ST-Bridge 임포트(H5).

### 부재 범위

- **철근 산정: 보·기둥만.**
- 슬래브·벽: 사용자가 입력한 형상으로 **콘크리트·거푸집 물량만.** 철근은 산출하지 않는다.

### 계산 상태

산출물의 사용 가능 범위는 상태가 결정한다. 우선순위는
`INPUT_INVALID` > `LEGAL_INVALID` > `LEGAL_REVIEW_REQUIRED` > `UNVERIFIED_RULE` > `VALID`.

| 상태 | 의미 | 허용 |
|---|---|---|
| `VALID` | 모두 통과 | 발주용 확정, 워터마크 없는 내보내기 |
| `UNVERIFIED_RULE` | 미검증 수치가 계산에 기여 | 파일럿 모드 확인 시에만 워터마크 내보내기. 확정 불가 |
| `LEGAL_REVIEW_REQUIRED` | 제79조 제2항 예외 주장 있음 | 내보내기 전부 차단. 외부 법규 검토 필요 |
| `LEGAL_INVALID` | 제79조 제1항 하한 미달 | 내보내기 전부 차단 |
| `INPUT_INVALID` | 입력 누락·참조 깨짐 | 내보내기 전부 차단 |

## 유저 플로우

### 여정 A — 도입 (첫 3개월)

```
 [1개월] 정보시스템부 보안 심사
    │      질문: "도면이 회사 밖으로 나가나?"
    └─→ 제출물: 실행 가능한 외부 엔드포인트 0건 리포트 + 런타임 아웃바운드 0 테스트 + CSP
                 + loopback 바인딩 + SBOM·라이선스·취약점 리포트
           ↓ 통과
 [2주] 파일럿 현장 1곳 (진행 중인 현장, 개발자 지원)
    │      기존 방식의 설계·소요물량 vs 우리 산출값을 엑셀로 수동 대조
    │      ※ 이 현장의 계약도서가 채택 기준을 확인한 곳이어야 한다 (H8)
    └─→ ★ 여기서 지금 없는 실적 검증 데이터가 생긴다 ★
           ↓
 [1주] H6 확인 → 사내 기준 차이 항목 수집
    └─→ 있으면 사내기준 덮어쓰기 착수. 없으면 만들지 않는다
           ↓
 [상시] 신규 현장부터 순차 적용
```

독립 검토자 승인 후라면 `VALID`로 대조하고, 승인 전이라면 일회성 파일럿 내보내기로
`UNVERIFIED_RULE` + 워터마크로 대조한다. 후자의 산출값은 발주·계약에 쓸 수 없고, 대조 리포트에
차이 원인을 분리할 수 없다는 한계를 함께 적는다.

```
 ① 프로젝트 설정
      · 현장명 · 층 · 통심 · 층고
      · 공공/민간 구분 · 채택 표준과 판 · 확인자 (GoverningStandard)
      · 부재종별·환경별 설계 피복표와 그 출처 (CoverPolicy)
      · 부재별 콘크리트 설계기준강도 · 철근 강종 · 이음 방식 기본값
      │
      ├─(A) PDF 구조도만 있음 ─→ 직접 입력 ─────────────────────────┐
      │   1) 층별 기둥·보 배치와 연결관계, 단면 부호 할당            │
      │   2) 기둥표·보표: 주근 직경/본수, 후프·스터럽 직경/간격/구간 │
      │      도면에 특기된 부재만 피복 예외값과 출처를 추가 입력      │
      │   3) 슬래브·벽 경계/두께/개구부 (철근은 입력·산출하지 않음)  │
      │   4) 입력 완전성·치수·참조 무결성 검증                       │
      │                                                              │
      └─(B) ST-Bridge(.stb) 있음 ─→ 조건부 임포트 ──────────────────┤
          절점/통심/층/배치/RC 단면/RC 배근 속성을 가져오고           │
          누락된 시공·적산 조건만 사용자가 보완                       │
                                                                     ▼
 ② 저장 및 배치 확인
      · IndexedDB 자동저장 + 프로젝트 JSON 저장/불러오기
      · 층별 2D 평면 뷰에서 배치를 눈으로 검증. 철근은 그리지 않음
      ▼
 ③ 배근상세·법규 검증
      · 입력된 설계 배근정보와 설계 피복값은 변경하지 않음
      · 표준 권장 피복은 별도로 산정해 참고 표시하고 입력값을 덮지 않음
      · 정착·이음·후프/스터럽 길이·본수 산정
      │
      ├─ 입력 누락            → INPUT_INVALID
      ├─ 미검증 룰 기여        → UNVERIFIED_RULE (파일럿 확인 시 워터마크 내보내기만)
      ├─ 제79조 제1항 위반     → LEGAL_INVALID, 해당 부재 평면 뷰에서 빨강
      ├─ 제79조 제2항 예외 주장 → LEGAL_REVIEW_REQUIRED
      └─ 모두 통과             → VALID
      ▼
 ④ 물량 확인 (VALID일 때만 발주용 확정 가능)
      · 철근 kg (설계수량 + 소요수량, 직경/강종/부재별)
      · 콘크리트 m³ · 거푸집 m² (설계수량, 부위별)
      │
      └─ 임의 숫자 클릭 → 【근거 패널】
          원본 입력 위치 → 기여 항목 → 공식/반올림 → 합계의 계산 DAG
          출처의 문서명·판·수정일·쪽·절·표·해시, 룰/엔진 버전
      ▼
 ⑤ 활용
      ├─ VALID           → 엑셀 물량표 + 감사 JSON
      └─ 파일럿 내보내기 → 매회 경고 확인 후 워터마크 + 미검증 기여 행 목록
```

## MVP 제외 사항

- **구조해석·구조설계·필요 주근량 결정** — 설계 배근정보는 입력이며 제품이 바꾸지 않음
- **제79조 이외의 포괄적 법규 적합성 판정** — "법규 전체 검증"으로 홍보하지 않음
- **제79조 제2항 예외의 자동 적합 판정** — `LEGAL_REVIEW_REQUIRED`로 차단하고 외부 검토로 보냄
- **슬래브·벽 철근 산출**
- **웹 콘솔·클라우드 동기화 일체** — 서버·DB·인증·조직 격리·전송 페이로드 전부 v1.1
- **3D 렌더링** — 뷰어는 층별 2D 평면
- **철근 렌더링·가공도·배근 시공상세도**
- **철근 절단 조합 최적화·가공장 발주 최적화**
- **2D 도면 자동 인식** (v2), **SRC 지원** (v2)
- **설계변경 전후 증감표** (v1.1), **실적 물량 대조 리포트** (v1.1)
- **범용 설치 패키징** — 준비된 파일럿 PC에서 개발자 지원 실행
- **릴리스 아티팩트 아카이빙·바이트 단위 재실행 보장** — 엔진 식별은 git commit SHA까지
- **문서 우선순위 자동 해석** — 계약도서·도면·특기시방이 상충하면 사람이 판단해 최종 값을 입력
- **멀티탭 편집 잠금, 룰 DSL, 결과 캐시**

## 성공 기준

실적 현장 검증 데이터가 없으므로 "실적 대비 오차 X% 이내"를 쓸 수 없다. 대신:

> **지원 범위의 모든 산출값을 원본 입력과 조항 근거까지 역추적하고,
> `validation-corpus/manifest`에 등록된 고정 케이스를 100% 통과한다.**

케이스마다 출처 판·쪽·절·표, 입력, 기대값, 반올림 정책, 검토자, 검토일을 기록한다.
**코퍼스에 등록되지 않은 기억 기반 기대값은 사용하지 않는다.**

## 가설과 go/no-go

| ID | 가설 | 통과 기준 |
|---|---|---|
| **H8** | 파일럿 현장의 계약도서가 공공건축공사 표준시방서를 채택한다 | 계약도서 명시 + 독립 검토자 서면 확인. **스텝 5의 하드 선행조건** |
| **H7** | 직접입력이 기존 수작업보다 충분히 빠르다 | 동일 대표 층 완료시간 중앙값이 기존의 70% 이하, blocking 오류 부재 100개당 1개 이하 |
| **H5** | PDF 구조도가 주 입력원이고 .stb를 갖고 있지 않다 | 3명 중 2명 이상 + 익명 샘플 1개 확보 시 STB를 MVP로 승격 |
| **H6** | 사내 기준이 표준시방서와 다르다 | 승인 이력·출처가 있는 상이 항목 1개 이상 |
| H1 | 철근 물량 산출에 상당한 수작업 시간을 쓴다 | 3명 중 2명 이상이 대표 1개 층에 1인일 이상 |
| H2 | 근거 추적성이 도입 동기가 된다 | 3명 중 2명 이상이 구체적 사용 장면 제시 |
| H3 | 설계변경 증감 산출이 최대 통증이다 | 3명 중 2명 이상이 상위 2개로 선택 시 UC-12 승격 검토 |
| H4 | 구조정보를 클라우드에 올릴 수 없다 | 실제 심사 문서가 외부 전송 금지·사전승인 요구 |

문턱은 **데이터 수집 전에 고정**했다. 결과를 본 뒤 움직이지 않으며, 바꿀 때는 이유·시점을 기록하고
이미 수집한 표본에 소급 적용하지 않는다.

## 배포 형태

제품 방향은 하이브리드(로컬 계산 + 본사 웹 집계)이나 **MVP 릴리스 1은 로컬 앱 단독**이다.

- 빌드된 정적 SPA를 `127.0.0.1`에만 바인딩한 로컬 서버로 실행 (Vite 개발 서버 아님)
- 프로젝트 데이터는 IndexedDB 자동저장 + 프로젝트 JSON 왕복
- 앱이 자동으로 외부에 보내는 것은 **없다.** 사용자가 만든 엑셀·감사 JSON·프로젝트 JSON만 로컬에 남는다

## 디자인

- 목적은 물량과 근거이며 시각화가 아니다. 화면은 **표 중심**이고 3D를 쓰지 않는다
- 배치 검증용 뷰어는 **층별 2D 평면**. 원본 구조도가 평면도라 대조가 쉽다. 철근은 그리지 않는다
- 외부 폰트·아이콘 CDN을 쓰지 않는다. 모든 에셋을 번들에 포함한다 (도입 심사 요건)
- 상태(`VALID` / 미검증 / 위반)는 색과 **고정 배너**로 구분한다. 부분 합계는 완전한 총량과 시각적으로
  구분되어야 하며 "부분 합계 — N개 부재 제외 · 발주 사용 금지"를 항상 표시한다
- UI 언어는 일본어. 부재 부호·배근 용어는 일본 실무 표기를 따른다

## 완료 판정

다음은 설명 문장이 아니라 자동 테스트 또는 재현 가능한 검수 시나리오여야 한다.

1. source registry가 모든 소스의 상태·판·해시·적용범위를 갖는다. `verified:true` 지원 룰에 독립 검토자·
   골든 케이스가 빠진 항목이 없고, `BIBLIOGRAPHY_ONLY`·`PENDING` 소스는 활성 룰이 아니다.
   표준상세도의 판 정합성 판정(사용/제외)이 기록되어 있다.
2. `GoverningStandard`에 공공/민간·채택 표준·판·확인자·확인일을 입력한다.
   미확정이면 `GOVERNING_STD_UNCONFIRMED`·`INPUT_INVALID`가 된다.
3. `CoverPolicy`에 부재종별·환경별 설계 피복값과 출처를 한 번 입력하면 모든 부재가 그것을 쓰고,
   도면 특기 부재만 `coverOverrideMm`으로 덮는다. 해당 항목이 없으면 `COVER_POLICY_MISSING`이 된다.
4. 층/통심뿐 아니라 기둥·보 배치와 연결, 보·기둥 설계 배근정보, 슬래브·벽 형상/개구부를 직접 입력한다.
5. 프로젝트 JSON 저장 → 새 세션에서 불러오기 → 정규화된 모델과 입력 해시가 동일하다. 동일
   `engineVersion`·`rulesetHash`에서는 같은 수량과 결정적 DAG가 복원된다. 다르면 과거 결과 복원이 아닌
   현재 버전 재계산이라는 고지가 먼저 표시된다.
6. 배근상세 실행 시 입력 주근 직경·본수·스터럽/후프 간격과 설계 피복값은 바뀌지 않고,
   권장 피복·정착·이음·길이·본수만 별도로 산정된다.
7. 철근 설계수량과 躯体 4% 할증을 적용한 소요수량, 콘크리트·거푸집 설계수량이 기준 반올림대로 나온다.
8. 할증률 룰에 골조 이외의 부재 구분(흙막이벽·말뚝 등)을 넣으면 값을 반환하지 않고 실패한다.
   "모든 철근 4%"로 일반화되지 않음을 테스트로 고정한다.
9. 임의 합계의 `rootTraceId`에서 모든 기여 항목을 거쳐 원본 `InputRef`와 잠긴 `SourceRef`까지 도달하고,
   `sum`·`multiply`·`round` 노드에서 산술 정합성이 성립하며 `rule` 노드는 `sourceRefs`가 비어 있지 않다.
10. 평시에 `verified:false` 룰을 의도적으로 주입하면 `UNVERIFIED_RULE`이 되고 내보내기가 차단된다.
11. 같은 결과에 일회성 `ExportContext.mode='pilot'`와 경고 확인을 제공하면 워터마크 산출물과 미검증 기여
    행 목록만 출력되고 발주용 확정은 차단된다. 다음 내보내기는 재확인 없이는 차단된다.
12. 제79조 제1항 하한 미달 유효 피복은 `LEGAL_INVALID`가 되고 해당 부재가 빨갛게 표시되며 파일럿에서도
    내보내기가 차단된다.
13. 제79조 제2항 인정 구조방법·인정부재 증빙을 입력하면 자동 적합 또는 `LEGAL_INVALID`로 단정하지 않고
    `LEGAL_REVIEW_REQUIRED`가 되며 정식·파일럿 내보내기가 모두 차단된다.
14. `VALID` 결과만 워터마크 없이 내보낼 수 있다. 내보내기는 항상 엑셀 물량표와 감사 JSON 두 파일을
    만들고, 감사 JSON에 입력 스냅샷·`TraceRecord[]`·`coverage`·`CalculationManifest`가 들어 있으며
    `ExportManifest.auditJsonSha256`이 그 파일의 실제 SHA-256과 일치한다.
15. 검증 코퍼스의 모든 지원 케이스가 통과하고, 지원 룰 매트릭스의 조건·예외·경계·반올림 분기가 각각
    하나 이상의 명명된 케이스에 연결된다. 케이스 0개인 룰은 지원으로 표시할 수 없다.
16. 성능 목표를 대표 모델에서 만족한다. 초과 시 한도를 문서화하고 경고를 표시한다.
17. 정규화 검증: ① 객체 키 삽입 순서 변경 ② 일본어 NFD 입력 ③ 집합 성격의 부재 배열 순서 변경은 같은
    입력 해시·총량·DAG ID를 낸다. 반대로 슬래브 경계점·배근구간처럼 의미 있는 배열의 순서를 바꾸면
    다른 입력으로 취급한다. `NaN`·`Infinity`는 거부하고 `-0`은 `0`과 같은 해시를 낸다.
18. 정적 검사에서 source registry 외 URL 문자열과 실행 가능한 외부 엔드포인트가 0건이고, 정본 URL은
    비클릭 텍스트다. 앱 실행 중 loopback 외 아웃바운드 요청이 0건이며, 서버는 `127.0.0.1`만 바인딩하고
    강화 CSP·서비스 워커 금지·SBOM·라이선스·취약점 리포트가 검수된다.
19. 입력 누락과 피복 하한 위반이 동시에 있는 모델은 `INPUT_INVALID`가 된다. 독립 계산 가능한 다른
    부재의 이슈는 계속 수집하되 상태 우선순위는 유지한다.
20. blocking 이슈가 있어도 예상 가능한 도메인 실패에서는 부분 수량·형상·`coverage`를 반환한다. UI는
    `coverage.excluded`에서 제외 부재 수와 ID를 고정 표시하고 `projectPath`·`memberId`로 문제 위치를
    지목한다. 부분 합계는 완전한 총량과 시각적으로 구분된다.
21. 의도적인 프로그래밍 예외를 주입하면 `compute()`가 이를 정상 도메인 이슈로 위장하지 않고 앱 오류
    경계가 실패 화면과 로컬 진단 JSON 저장을 제공한다.
22. 스터럽 간격 0, 부재 길이 0, 정착길이가 부재 길이를 초과하는 입력이 각각 `NON_POSITIVE_VALUE`·
    `LENGTH_INFEASIBLE`로 잡히고 0으로 나누기가 발생하지 않는다.
23. IndexedDB를 비활성·용량 초과 상태로 만들면 실패가 화면에 지속 노출되고 조용히 사라지지 않는다.

조건부 스텝을 착수하면 추가된다.

24. (STB) 대표 `.stb` 샘플에서 배치·RC 단면·보/기둥 배근 속성을 읽어 직접입력과 같은 모델을 만들고 같은
    결과를 낸다. 외부 엔티티를 참조하는 악성 XML과 엔티티 확장 폭탄이 파싱 단계에서 거부된다.
25. (사내기준) 허용 적산값을 덮어쓰면 결과와 트레이스가 바뀌고 승인 정보가 표시된다. 제79조 validator를
    덮어쓰려 하면 JSON 전체가 거부된다.
