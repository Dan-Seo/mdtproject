# Architecture Decision Records

## 철학

MVP·프로토타입이다. 가설을 검증할 수 있는 최소 구현만 만든다. 다만 두 가지는 타협하지 않는다.

1. **근거 추적성** — 모든 산출값이 원본 입력과 규정 조항까지 역추적된다. 이 제품의 유일한 차별점이다
2. **미검증 수치 fail-closed** — 독립 검토를 거치지 않은 규정 수치는 정식 결과를 만들 수 없다

번호 **007·013·018·025·026·028·029·032**는 웹 콘솔·멀티탭 잠금 관련 결정이었고 MVP 축소에서
제거했다. **재사용하지 않는다** — v1.1에서 웹 콘솔을 만들 때 원래 번호로 복원한다.

---

## 기반

### ADR-001: TypeScript 워크스페이스 2개
**결정**: `packages/core` + `apps/local`. `apps/web`은 만들지 않는다.
**이유**: 1인 개발. 순수 로직과 앱을 분리하되 그 이상 쪼개지 않는다.
**트레이드오프**: 네이티브 성능을 포기한다.

### ADR-002: `core`는 결정적 순수 함수
**결정**: 파일·DB·네트워크·`Date.now()`·`Math.random()`을 `core`에서 쓰지 않는다.
**이유**: 테스트·재현성·환경 독립. 결과 비영속화(ADR-023)의 전제다.
**트레이드오프**: 파일 접근이 전부 앱 레이어로 이동한다.

### ADR-006: Vite + React 로컬 브라우저 앱
**결정**: Electron 대신 브라우저에서 도는 정적 SPA.
**이유**: MVP에 데스크톱 패키징이 불필요하다.
**트레이드오프**: 준비된 PC와 로컬 서버가 필요하다. `file://`는 IndexedDB origin 제약으로 불가.

### ADR-009: 모델 변환은 순수 함수, 인플레이스 수정 금지
**결정**: `ProjectModel`을 직접 수정하지 않고 새 객체를 반환한다.
**이유**: v1.1 설계변경 증감표(UC-12)를 위해 전후 상태가 동시에 필요해진다.
**트레이드오프**: 객체 직접 수정의 편의를 포기한다.

## 제품 범위

### ADR-003: 구조설계가 아니라 설계 배근정보 기반 상세 산정
**결정**: 주근 직경·본수·간격은 입력이며 제품이 바꾸지 않는다.
**이유**: 책임 범위와 입력을 명확히 한다. 구조설계 책임을 지지 않는다.
**트레이드오프**: 주근 자동설계를 포기한다.

### ADR-011: 철근은 그리지 않음
**결정**: 뷰어에 철근을 렌더링하지 않는다. 철근은 표로 본다.
**이유**: 목적이 물량과 근거다.
**트레이드오프**: 시공상세 시각화를 포기한다.

### ADR-034: 뷰어는 층별 2D 평면
**결정**: 3D 라이브러리를 쓰지 않고 층별 평면 뷰로 배치를 검증한다.
**이유**: 원본 구조도가 평면도라 대조가 더 쉽다. 3D는 번들·성능·별도 스텝을 끌고 오면서 어떤 가설에도
기여하지 않는다.
**트레이드오프**: 입체적 확인을 포기한다.

### ADR-033: 웹 콘솔·클라우드 동기화를 v1.1로 이관
**결정**: 서버·DB·인증·세션·조직 격리·전송 페이로드를 MVP에서 전부 뺀다.
**이유**: 어떤 MVP 가설도 웹 콘솔로 검증되지 않는데 로드맵의 20%와 방어 설계를 소모한다. 게다가
아웃바운드 0이 도입 심사에서 전송 허용목록보다 강한 증명이 된다.
**트레이드오프**: 본사 실시간 집계를 포기한다. 파일럿 기간에는 담당자가 엑셀을 보낸다.

### ADR-014: 설계수량과 소요수량을 분리
**결정**: `designQuantity`와 `requiredQuantity`를 별도 필드로 둔다.
**이유**: 기준상의 의미(設計数量/所要数量)와 발주 용도가 다르다.
**트레이드오프**: 단일 총량 UI의 단순함을 포기한다.

### ADR-017: 할증률 룰은 부재 구분을 인자로 받고 범위 밖이면 실패
**결정**: 골조 4%를 반환하되 흙막이벽·말뚝 등이 들어오면 값을 주지 않고 실패한다.
**이유**: 같은 기준서가 흙막이벽 3%(13쪽), 말뚝 3%(14쪽)로 다르게 정한다. "모든 철근 4%"로
일반화하면 조용히 틀린 값이 나간다.
**트레이드오프**: 미지원 부재의 개략 산출이 불가능하다.

## 규정과 검증

### ADR-005: 생성 룰과 봉인된 제79조 validator/예외 주장 분리
**결정**: 시행령 제79조 제1항 피복 하한 검사는 어떤 경로로도 덮어쓸 수 없는 봉인된 validator에 둔다.
**이유**: 사내기준이 법정 하한을 우회하면 제품이 위법을 통과시킨다.
**트레이드오프**: 포괄 법규 판정과 예외 자동 판정을 포기한다.

### ADR-008: 미검증 룰은 fail-closed
**결정**: `verified:false` 수치가 하나라도 계산에 기여하면 `UNVERIFIED_RULE`이 되고 발주용 확정과
정식 내보내기를 차단한다. 유일한 예외는 ADR-015.
**이유**: 기억으로 채운 규정 수치는 그럴듯하지만 틀린다. 발주용 오사용을 막는다.
**트레이드오프**: 초기 데모 범위가 좁아진다.

### ADR-015: 미검증 결과는 일회성 `ExportContext.mode='pilot'` 확인 때만 워터마크 내보내기
**결정**: 계산 상태는 `UNVERIFIED_RULE` 그대로 두고, 내보내기 시점에 사용자가 경고를 재확인한
경우에만 워터마크 산출물을 허용한다. 지속 플래그를 `ProjectModel`에 저장하지 않는다.
**이유**: 검토자 확보 전에도 파일럿 대조를 돌려야 검증 데이터가 생긴다. 그러나 파일럿 권한이
프로젝트 데이터에 남으면 계산 상태와 권한이 뒤섞인다.
**트레이드오프**: 내보낼 때마다 확인해야 한다.

### ADR-036: 프로젝트별 `GoverningStandard` 필수, 문서 우선순위는 코드가 해석하지 않음
**결정**: 공공/민간 구분과 채택 표준·판·확인자를 프로젝트마다 기록하고 미확정이면 계산을 차단한다.
계약도서·도면·특기시방의 우선순위는 코드가 해석하지 않고 사람이 최종 값을 입력한다.
**이유**: 공공건축공사 표준시방서는 관청영선이 **관청시설**에 쓰는 기준이며 민간공사의 보편
기본값이 아니다. 다만 우선순위 그래프는 MVP에 소비하는 코드가 없다.
**트레이드오프**: 초기 입력·검토 부담이 늘고, 문서 상충의 자동 해소를 포기한다.

### ADR-037: 제79조 제2항 예외 주장은 `LEGAL_REVIEW_REQUIRED`
**결정**: 인정 구조방법·인정부재 주장이 있으면 자동 적합 판정도, `LEGAL_INVALID` 판정도 하지 않고
별도 상태로 차단하며 증빙 `InputRef`를 남긴다.
**이유**: 합법 가능성이 있는 부재를 위법으로 단정하면 공무부에게 최악의 오류다. 반대로 자동 통과시키면
회사가 임의로 하한을 내리는 통로가 된다.
**트레이드오프**: 예외가 있는 프로젝트는 자동 처리할 수 없다.

### ADR-022: 룰 로직은 코드, 룰 수치는 데이터
**결정**: 로직은 평범한 TS 함수, 수치는 `verified`·`SourceRef`가 붙은 데이터 파일.
**이유**: 수치가 코드에 리터럴로 박히면 항목 단위 `verified` 게이트가 성립하지 않는다.
**트레이드오프**: 파일 2종을 관리해야 한다. 룰 DSL·평가기는 만들지 않는다.

### ADR-010: 사내기준은 승인 메타데이터가 있는 로컬 JSON
**결정**: 출처·승인자·승인일·해시가 필수인 로컬 JSON으로 적재한다. (조건부 스텝 12)
**이유**: 중앙 배포 시스템을 미룬다.
**트레이드오프**: 중앙 통제가 불가능하다.

### ADR-035: 사내기준 덮어쓰기는 H6 확인 후 조건부 스텝
**결정**: H6(사내기준이 실제로 다른가)이 확인되기 전에는 덮어쓰기 기능을 만들지 않는다.
**이유**: 계획이 스스로 "H6이 틀리면 덮어쓰기 기능이 불필요"라고 적어둔 항목이다.
**트레이드오프**: 초기 릴리스에서 사내값을 반영할 수 없다.

## 근거 추적

### ADR-004: 근거를 부모 참조가 있는 계산 DAG로 기록
**결정**: 평면 로그가 아니라 `parentTraceIds`로 이어진 DAG를 만든다.
**이유**: 철근 중량은 본래 (순길이 + 정착 + 이음) × 단위질량 × 본수라는 트리라서 평면 목록으로는
설명이 되지 않는다.
**트레이드오프**: 단순 로그보다 구현량이 늘어난다.

### ADR-016: DAG는 증거이며 재실행하지 않음
**결정**: 저장된 DAG를 다시 실행해 합계를 재현하지 않는다. 대신 노드별 산술 정합성을 검사한다.
**이유**: 재실행 요구는 계산 엔진을 두 벌 만드는 일이다.
**트레이드오프**: 완전 재현 테스트 대신 `operation`별 정합성 검사로 대체한다. `rule` 노드는 산술
검사가 불가능해 골든 케이스 회귀로 검증한다.

### ADR-019: 트레이스는 결과 객체에 동봉
**결정**: collector를 주입해 push 하지 않고 각 단계가 결과와 트레이스를 함께 반환한다.
**이유**: ADR-002의 순수성을 유지한다.
**트레이드오프**: 반환 타입이 무거워진다.

### ADR-040: 엔진 식별은 git commit SHA. 감사 산출물은 xlsx + 동봉 JSON
**결정**: `engineVersion`에 빌드 시 commit SHA를 주입한다. 릴리스 매니페스트·아티팩트 아카이빙을
만들지 않는다. 감사 산출물은 사람이 읽는 엑셀과 기계가 읽는 JSON으로 나눈다.
**이유**: 버전 문자열이 실제 실행물을 지목하지 못하는 문제는 commit SHA로 해소된다. 아티팩트
아카이빙과 8시트 통합문서는 2주 파일럿 대비 과하고, 수만 행 DAG 시트는 아무도 읽지 않는다.
**트레이드오프**: 바이트 단위 재실행 보장과 단일 파일 산출물을 포기한다.

## 실행과 오류

### ADR-020: 예상 가능한 도메인 실패는 throw 대신 `Issue[]` 반환
**결정**: 입력 누락·참조 깨짐·규정 위반은 `Issue[]`로 돌려준다.
**이유**: 순수 함수와 정합적이고 UI가 `projectPath`·`memberId`로 위치를 지목할 수 있다.
**트레이드오프**: 호출부가 항상 issues를 검사해야 한다.

### ADR-030: `compute()`는 도메인 실패에서 부분 결과 + `issues` + `coverage` 반환
**결정**: 계산 가능한 범위의 `quantities`·`traces`·`geometry`를 항상 함께 돌려준다. 다만 프로그래밍
오류·메모리 고갈까지 삼키지 않고 앱 오류 경계로 넘긴다.
**이유**: 부재 1000개 중 3개가 깨졌다고 전체를 중단하면 무엇을 고칠지 알 수 없다. 반대로 모든 예외를
`Issue`로 위장하면 진짜 버그가 숨는다.
**트레이드오프**: 반환 타입과 UI가 무거워지고, 불완전 결과 노출은 상태 게이트로 방어한다.

### ADR-041: 부분 결과는 `ResultCoverage` 하나로 표현
**결정**: 행 단위 불완전성을 `QuantityRow`에 필드로 두지 않고 `coverage.excluded`에서 파생한다.
**이유**: 같은 사실의 진실 원천이 둘이면 어긋난다.
**트레이드오프**: UI가 조회를 한 번 더 한다.

### ADR-021: `compute()` 단일 진입점
**결정**: 단계별 함수를 공개 API로 노출하지 않는다. 예외는 `validateProject()`뿐.
**이유**: 단계를 쪼개면 앱이 처리 순서(적용 기준 → 생성 룰 → 봉인 validator → 물량)를 우회할 수 있다.
**트레이드오프**: 부분 재계산이 불가능하다.

## 저장과 재현성

### ADR-023: 작업 프로젝트는 입력만 저장, 내보낼 때 감사 JSON 생성
**결정**: 자동저장과 프로젝트 JSON은 `ProjectModel`만 담는다. 결과·트레이스·manifest는 재계산으로
복원하고, 내보낼 때만 감사 JSON으로 고정한다.
**이유**: 트레이스 노드가 대표 모델에서도 수천~수만 개라 저장하면 용량·쓰기 성능이 병목이 된다.
발주 근거는 파일로 남으면 충분하다.
**트레이드오프**: 작업 재개 시 매번 재계산한다.

### ADR-031: 해시 전 키 정렬·NFC·합산 순서 고정
**결정**: 해시 계산 전 재귀 키 정렬, 모든 사용자 문자열 `normalize('NFC')`, 결정적 키 정렬 후 합산.
**이유**: 재현성 선언의 기본 전제다. 일본어 부재 부호를 다루므로 NFC는 선택이 아니다 —
macOS는 NFD, Windows는 NFC로 입력된다.
**트레이드오프**: 정규화 비용.

### ADR-039: 집합 배열 정렬·순서 배열 보존·숫자 표준화·결정적 ID
**결정**: 집합 배열(부재·층·단면)은 안정 ID로 정렬하고 순서 배열(경계점·배근구간)은 보존한다.
`NaN`·`Infinity` 거부, `-0` → `0`. `TraceRecord`·`QuantityRow` ID는 안정 입력 경로·`ruleId`·순번의
해시로 만든다.
**이유**: ADR-031의 키 정렬만으로는 배열 순서가 정규화되지 않고, 경계점까지 정렬하면 형상이 바뀐다.
ID가 난수·시각 기반이면 "동일 DAG"가 애초에 테스트 불가능하다.
**트레이드오프**: 도메인별 canonicalizer가 필요하다.

### ADR-024: 형상은 `core`가 소유
**결정**: `core/src/geometry/`가 형상을 만들고 뷰어는 2D 평면으로 투영만 한다.
**이유**: 콘크리트 체적과 거푸집 면적이 형상에서 나오므로, 앱이 따로 만들면 화면과 물량이 어긋난다.
**트레이드오프**: `core`가 무거워진다.

### ADR-012: 현재 프로젝트 자동저장 + JSON 왕복은 MVP
**결정**: IndexedDB 자동저장과 버전이 붙은 프로젝트 JSON 저장/불러오기를 MVP에 넣는다.
**이유**: 파일럿에서 새로고침·재시작에 견디는 지속성이 없으면 쓸 수 없다.
**트레이드오프**: 이력·스냅샷 비교는 v1.1로 미룬다.

## 보안 경계

### ADR-027: 로컬 앱은 외부 네트워크 요청 0
**결정**: 아웃바운드를 만들지 않는다. loopback 전용 서버, 강화 CSP(`connect-src 'none'`), 서비스 워커
금지, 모든 에셋 번들 포함. 정본 URL은 비클릭 텍스트로만 렌더링한다. SBOM·라이선스·취약점 자료를
심사에 함께 제출한다.
**이유**: 도면을 보유한 PC의 아웃바운드가 도입 심사의 핵심이다. 전송 경로를 만들지 않으면 그 경로를
방어할 필요도 없다.
**트레이드오프**: CDN·웹폰트·원격 에러 리포팅을 포기한다. 아웃바운드 0이 심사 자동 통과를 보장하지는
않는다.
