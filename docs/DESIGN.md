## 3. 상호 선택 모델

내역서 행 ↔ 3D 철근 ↔ 평면 부재를 잇는 축이 두 개다. **이게 이 제품의 핵심 상호작용이다.**

### 3.1 부재 그룹 선택 — `sel`

```js
sel = { group: '1F|C|C1', memberId: '1F-X2Y2' }
```

`group`은 `{층 또는 레벨}|{C|G}|{符号}`. 같은 符号의 부재는 한 그룹으로 묶여 내역서에 **1행 + 箇所수**로 집계된다(9개 기둥 → 1행 × 9箇所). `memberId`는 그 그룹의 대표 1개 — 3D에 실제로 그려지는 부재.

| 조작 | 결과 |
|---|---|
| 평면에서 부재 클릭 | `sel` 갱신 → 3D가 그 부재를 그리고, 내역서가 해당 그룹으로 자동 스크롤 |
| 내역서 그룹/행 클릭 | `sel` 갱신 → 3D 갱신, 평면 강조 |
| `sel` 변경 | 그 부재가 속한 층으로 평면 탭이 **자동 전환** |

선택 표시는 오렌지 하나로 통일: 채움 `rgba(245,78,0,.05~.14)`, 테두리·글자 `--color-primary`.

### 3.2 철근 행 강조 — `hoverRow`

`sel`과 **별개 축**이다. 값은 행 id(`1F|C|C1|main`).

| 조작 | 결과 |
|---|---|
| 내역서 행에 hover | 3D에서 그 행의 철근만 오렌지(`#f54e00`)로, 나머지는 회색(`#b8b3a6`) |
| 내역서 행에 **포커스** | 위와 동일 |
| 3D에서 철근 클릭 | 레이캐스트 → `rowId` 역추적 → 해당 내역서 행 강조 |

PRD 핵심 기능 4번 "내역서 행 ↔ 3D 철근 개체 상호 선택"이 이 축이다.

**포커스가 hover와 동등한 트리거인 것은 이름과 어긋나지만 의도된 것이다.** 프로토타입은 hover 전용이었고 그대로 옮기면 이 축 전체가 마우스 없이는 도달 불가능해진다 — 두 축 중 하나가 키보드 사용자에게서 통째로 사라지는 셈이다(docs/UX.md §3.5). 상태 이름 `hoverRowId`는 저장소 전역에 퍼져 있어 유지하고, **트리거만 hover ∪ focus로 넓힌다.** 이름을 고치려면 별도 리네임 커밋으로 한다.

### 4.1 算出式 디스클로저

행을 열면 mono `<pre>`로 산출 과정이 그대로 나온다. PRD의 "행 단위 산출식"이 이것이다(계산 DAG는 MVP 제외).

```
加工長 ＝ 2×{(800−2×40)＋(800−2×40)} ＋ 2×135°フック余長 6d(78) ＝ 3040
本数 ＝ ⌈(階高 4200 − 上部大梁せい 750) ÷ 100⌉ ＋ 1 ＝ 36
```

읽는 사람이 표 값을 손으로 재현할 수 있어야 한다 — 숫자만이 아니라 **어느 규준값이 어디에 들어갔는지**가 문장에 남는다.

### 4.2 CSV 내보내기

화면 13열 + `階 / 部材 / 符号` 3열 + `算出式` 1열 = **17열**. 파일 앞머리에 §5의 워터마크 2줄이 먼저 온다. `﻿` BOM 포함(Excel 한글·일본어 깨짐 방지), 파일명 `kijun-takeoff.csv`.

> CSV는 프로토타입 단계의 대용이었다. **제품은 exceljs 기반 `.xlsx`로 구현돼 있다**(`src/lib/export/`) — 17열 구성과 워터마크 위치는 동일하다. PDF·glTF는 여전히 미구현.

## 5. inferred 경고와 워터마크

PRD 핵심 기능 5번의 UI 구현. **3단계로 중첩**해서 놓친 사람이 없게 한다.

| 단계 | 위치 | 표시 |
|---|---|---|
| 1 | 철근 행 이름 옆 | crimson 경고 삼각형 + 툴팁에 기여한 항목명 |
| 2 | 出典 칩 | 테두리·글자가 `--color-error`로 바뀜 |
| 3 | 내보낸 파일 첫 줄 | `※ 未確認の規準値を含む — 検収前の参考値` |
| 3 | 내보낸 파일 둘째 줄 | 기여한 inferred 항목 전체 목록 (규준명·조항 포함) |
| 3 | 항목명 셀 | `⚠ ` 접두사 |

전파 규칙: 철근 행의 `rules[]` 중 하나라도 `inferred`면 그 **행 전체가 inferred**다. 행이 하나라도 inferred면 산출물 전체에 워터마크가 붙는다. 부분 워터마크는 없다 — 어느 숫자가 오염됐는지 사용자가 추적하게 만들지 않는다.

## 6. 출처 표시 UI

**법적 의무다**(PDL1.0 준거, CLAUDE.md CRITICAL). 제거 대상이 아니다.

칩 하나가 규준 하나에 대응한다. 표기는 `{약칭} {조항}` — 예: `標準仕様書 5.3.4`.

- 클릭 → 원문 URL 새 탭 (`e.stopPropagation()`으로 행 선택과 분리)
- hover 툴팁 4줄: `라벨 ＝ 값` / `문서명(판) 조항 쪽` / (inferred면) `⚠ 未確認 —` / 주석
- 10px mono, 4px radius, 1px 테두리

출처 데이터 구조:

```js
KJ_SOURCES.spec = { short:'標準仕様書', doc:'公共建築工事標準仕様書（建築工事編）',
                    ed:'令和4年版', pub:'国土交通省 大臣官房官庁営繕部', url:'…' }
KJ_RULES['lap.L1'] = { label:'重ね継手長さ L1（フックなし）', expr:'40d',
                       src:'spec', sec:'5.3.4 表5.3.2', page:'5-12',
                       confidence:'…', note:'SD345 / Fc 21–27 N/mm²。' }
```

룰팩 YAML로 옮길 때 이 필드 집합을 그대로 유지한다. UI가 `doc`·`ed`·`sec`·`page`·`url`을 전부 쓴다 — 하나라도 빠지면 툴팁이 비고 고지 의무를 못 채운다.

## 7. 3D 뷰어

- 좌표계: **mm**, `X` = 평면 x, `Y` = 높이, `Z` = 평면 y. 씬에는 `×0.001`로 스케일해서 넣는다.
- 3D 페인은 **페인-로컬 탭 「部材｜建物」 2모드**다. 페인 헤더의 탭은 平面 페인의 StoryTabs 선례를 따르며, 라우팅·위저드가 아니므로 UX.md §3.2의 단일 화면 원칙과 충돌하지 않는다.
  - **部材 탭(기본)**: 선택된 부재 1개의 배근만 렌더한다.
  - **建物 탭**: 활성 안건 **전 부재**의 콘크리트 외형 + 柱 배근을 렌더한다. 철근은 표시 반경별 `InstancedMesh`(R4 대응), 콘크리트는 부재별 Mesh. 大梁 배근은 M3 이후. 부재 클릭은 `sel`을 갱신해 4페인 상호 선택과 연동하지만 **모드를 자동 전환하지 않는다.** 층간 定着·継手가 시각적으로 겹쳐 보이는 것은 R7(이중 계상)이라는 domain 사실의 표시이지 렌더 버그가 아니다.
- 부재 외형은 `EdgesGeometry` 와이어프레임(`#4a483c`) + **반투명 콘크리트 솔리드**(`#55524a`, opacity 0.14, depthWrite 끔)로 암시한다. 솔리드는 피킹 대상이 아니다 — 철근이 주인공인 원칙은 유지된다.
- 철근은 꺾인점 사이를 8각 실린더로 잇는다. 帯筋/あばら筋은 `closed:true`로 폐합.
- **표시 배치 규칙**: 표시 반경이 과장돼 있으므로(아래 예외 2) domain 중심선을 그대로 그리면 帯筋과 主筋이 관통한다. 帯筋 중심선은 かぶり면에서 표시 반경만큼 안쪽(바깥면이 かぶり면에 접함), 主筋 축은 かぶり 모서리에서 帯筋 표시 지름 + 主筋 표시 반경만큼 안쪽(표면이 帯筋 안쪽면에 접함)에 놓는다. 수량 계산의 근거인 domain points는 불변이다.
- 재질: 철근 `#b8b3a6` (roughness .35 / metalness .6), 강조 시 `#f54e00` + emissive. `RoomEnvironment` 환경맵(PMREM)과 ACES 필믹 톤매핑·sRGB 출력이 금속 재질의 전제다 — 환경맵 없는 metalness는 탁하게 죽는다.
- 조명·공간감: HemisphereLight 0.5 + DirectionalLight 1.8(그림자 캐스트, 2048 맵, 콘텐츠 바운즈에 맞춤). 바닥은 콘텐츠 최저점에 그리드 + 그림자 수용 평면. fog는 배경과 같은 `#1b1a14` — 다크 캔버스 예외(아래 1)의 확장이지 새 예외가 아니다. 그라데이션 배경은 도입하지 않는다.
- 카메라: fov 38, 방향 `(0.72, 0.34, 0.86)` 정규화, 바운딩박스 8꼭짓점을 투영해 여유 1.08로 자동 프레이밍. OrbitControls damping 0.08.
- **카메라 연출**: 첫 로드는 자동 프레이밍 포즈에서 yaw를 틀고 거리를 1.35배 벌린 시작 포즈로부터 900ms 이징(easeOutCubic) 플라이인, 이후 선택 전환은 550ms 보간. 사용자 입력(`start` 이벤트)이 오면 연출을 즉시 중단한다 — 사용자가 항상 이긴다. 유휴 8초 후 슬로우 오토로테이트, 입력 시 해제.

**의도적 예외 2건** (디자인 시스템 규칙 위반이지만 유지):

1. 캔버스 배경이 다크 `#1b1a14`. DS는 "한 페이지에 배경색 2개(크림·화이트)"를 규정하지만, 회색 철근을 크림 위에 놓으면 대비가 죽는다.
2. 철근 반경을 `max(径, 14) × 1.6`으로 과장했다. **실경 축척이 아니다.** D10이 실제 비율대로면 화면에서 사라진다. 치수 판독용이 아님을 UI에 명시할 것.

## 8. i18n

`ja`(기본) / `ko` 두 로케일. 헤더 우측 토글로 즉시 전환.

**도메인 용어는 번역하지 않는다** (ADR-008). `ko` 로케일에서도 `柱`·`大梁`·`主筋`·`帯筋`·`あばら筋`는 일본어 원어 그대로다. 번역 대상은 UI 레이블(`길이`, `본수`, `설계수량`)뿐이다.

한국 실무자 UX 리뷰(M5)가 이 로케일 위에서 이뤄진다. PRD의 검증 분리 — 한국 실무자는 UX만, 숫자는 골든테스트 — 를 UI가 흐리지 않아야 한다.

## 9. 디자인 시스템 자체의 불일치

`design/kijun-design-system/readme.md`를 그대로 믿으면 안 되는 지점들. 원문은 손대지 않고 반입했다.

| 불일치 | 내용 | 판단 |
|---|---|---|
| **브랜드 서사가 다른 제품** | readme는 Kijun을 "저장소 전체를 읽는 에디터"라는 개발자도구로 설명한다. 마케팅 사이트·가격표·블로그·에이전트 타임라인이 컴포넌트 인벤토리에 있다. 실제 Kijun(基準)은 배근·물량 산출 도구다 | **토큰은 그대로 쓴다.** 브랜드 카피·CONTENT FUNDAMENTALS·타임라인 파스텔 5색은 대상 제품이 달라 적용 대상 아님 |
| **Index의 절반이 존재하지 않음** | readme가 `components/`, `guidelines/`, `ui_kits/`, `templates/`, `assets/`, `SKILL.md`를 나열하지만 반입한 프로젝트에는 토큰·`styles.css`·`_ds_bundle.js`뿐 | 컴포넌트 구현은 `_ds_bundle.js` 안에만 있음(16종). 소스 JSX 없음 |
| **hover 정책 모순** | readme: "hover는 소스 브랜드에 정의돼 있지 않으며 여기서 발명하지 않는다 — press와 focus만" | 프로토타입은 hover가 **핵심 상호작용**이다(행↔3D 강조, 출처 툴팁). 제품 쪽이 옳다. DS 문서를 갱신할 것 |
| **폰트가 대체품** | KijunGothic 라이선스 미보유 → Inter로 대체 | 실무상 문제 없음. 단 CJK 글리프는 Inter에 없어 시스템 폰트로 폴백된다 — 일본어 UI에서 자간·리듬이 readme 설계와 달라짐 |

## 10. 반입물이 프로젝트 규칙과 충돌하는 지점

프로토타입 소스(`app/*.js`, `app/*.jsx`)는 **저장소에 반입하지 않았다.** TDD 가드 훅이 차단했고, 아래를 보면 그 판단이 맞다. 프로토타입은 화면 사양의 근거일 뿐 구현 출발점이 아니다.

| # | 항목 | 위치 | 충돌 | 조치 |
|---|---|---|---|---|
| 1 | **규준 수치가 코드에 이중 선언** | `engine.js` — `V={coverC:40, coverB:40, L1:40, L2:35, h90:8, h135:6}` | **ADR-002 CRITICAL.** 룰팩은 `expr:'40d'` 문자열을 표시용으로만 갖고, 계산은 별도 JS 상수가 한다. 표시값과 계산값이 갈릴 수 있는 구조 | 룰팩 YAML을 유일 출처로. 조회 함수가 숫자를 반환하고 UI·엔진이 같은 값을 본다 |
| 2 | **할증률이 무조건 1.04** | `engine.js` — `reqKg = designKg * V.markup` | **ADR-014.** 부재 구분을 인자로 받아야 하고, 범위 밖이면 기본값 4%를 주지 말고 실패해야 함 | `markup(memberClass)` 시그니처. 흙막이벽·말뚝 3%는 MVP 범위 밖이지만 시그니처는 지금 정한다 |
| 3 | **`confidence: 'verified'`** | `rulepack.js` — 8개 중 6개 | CLAUDE.md의 어휘는 `stated` / `inferred`다. 게다가 파일 헤더가 "デモ用のプレースホルダであり、原文抽出の結果ではない"라고 스스로 밝힌다 → `verified`는 **이중으로 틀렸다** (ADR-015, R6) | 어휘를 `stated`/`inferred`로 교정. M0 전에는 전부 `inferred` |
| 4 | **출처 없는 산출 규칙** | `engine.js` — `r10 = 10mm 올림` | 모든 길이에 적용되는데 근거 문서가 없다 | 수량적산기준에서 근거를 찾아 룰팩 항목화하거나, 없으면 `inferred`로 명시 |
| 5 | **상부 大梁せい 상수** | `engine.js` — `beamDepthAbove: 750` | 帯筋 본수 `⌈(階高 − 750) ÷ 피치⌉ + 1`에 직접 들어간다. 부재별 사실을 전역 상수로 굳힘 | 단면일람에서 해당 층 大梁 せい를 조회 |
| 6 | **CDN 의존** | `index.html` — React·Babel·three.js(unpkg), Google Fonts | 도면 데이터가 실려 나가진 않으므로 CRITICAL 위반은 아니다. 다만 외부 요청이 5건 생기고 오프라인에서 죽는다 | Next.js 번들 + `next/font` 셀프호스팅 |
| 7 | **철근 1개당 Mesh 1개** | `Viewer3D.jsx` | **R4** — 층당 1만 개 규모에서 `InstancedMesh` 필수 | **해소.** 部材 뷰는 세그먼트가 아니라 **내역서 행 단위로 지오메트리를 병합**한다 — 柱 1개가 세그먼트 156개여도 메시는 2개(主筋·帯筋)이고, 강조 단위가 곧 행이라 재질 교체도 1회로 끝난다. 다부재를 동시에 그리는 **建物 뷰는 표시 반경별 `InstancedMesh`**로 구현됐다(§7) |
| 8 | **골조가 하드코딩** | `engine.js` — `SECTIONS`·`STORIES`·`LEVELS` (3×3 그리드 6000, 2층) | 프로토타입으로는 정당. 다만 M1 입력 UI가 대체해야 할 대상이 정확히 이것 | 평면 편집 + 단면일람 입력으로 대체 |

**1·2·3번은 구현 전에 반드시 해소한다.** 프로토타입 로직을 그대로 옮기면 세 개의 CRITICAL 규칙을 한 번에 깬다.

## 부록: 프로토타입 소재

**프로토타입 소스는 저장소에 없다.** 화면 사양은 이 문서로 전부 옮겼고, 소스를 옆에 두면 §10-1·2·3을 그대로 베낄 위험이 실질적이라 반입하지 않았다.

동작을 눈으로 봐야 하면 원격 디자인 프로젝트에서 연다:

```
https://claude.ai/design/p/5b8804ed-775d-4ad9-a490-d36698c90f32
```

로드 순서만 여기 남긴다 — 의존 구조 자체가 사양이기 때문이다. 토큰 CSS 7개 → `_ds_bundle.js` → `rulepack` → `i18n` → `engine` → 컴포넌트 4개. **룰팩이 엔진보다 먼저 와야 한다**는 제약이 여기서 드러나고, 이건 제품에서도 유지된다.
