# Step 2: cutoff — ［］ 안의 カットオフ 치수를 원문으로 보존한다

`yokohama-p14`의 表題 特記는 `3.［］内はｶｯﾄｵﾌの柱面からの寸法を示す。`라고 말한다.
그 치수는 모델의 `GirderSection.main.cutoffFromSupportFaceMm`와 **같은 뜻**이다
(둘 다 「柱面에서 안쪽으로 몇 mm」).

**그런데 이 step은 값을 채우지 않는다.** 채울 수 없다 — 아래 「왜 raw까지인가」를 반드시 읽어라.
지금 파서는 ［］를 통째로 무시하고 있고, 이 step은 그것을 **원문 보존**까지 한 칸 옮긴다.
사용자가 断面一覧에서 손으로 옮겨 적을 수 있게 하는 것이 목적이다.

## 왜 raw까지인가 (설계 판단 — 뒤집지 마라)

모델의 `cutoffFromSupportFaceMm`는 **断面당 숫자 하나**다. 반면 도면의 ［］는 **位置별**로 붙는다
(아래 실측 참조 — ［2500］가 `内端` 열 위에 있고 `外端` 열 위에는 없다).

カットオフ筋이 존재한다는 것은 端部와 中央의 主筋 本数가 다르다는 뜻이고, 픽스처의 해당 符号는
전부 **좌우 端部의 本数까지 다르다**(`外端 8 / 中央 8 / 内端 13`). 그래서 그 후보들은 이미
`girderMain`이 빈칸이고 `主筋端部左右相違` issue가 붙어 있다 — **R13**이다.

즉 カットオフ를 값으로 채우는 일은 R13(`GirderMainRow`가 양단 동값만 담는 모델 제약)이
닫힌 뒤에야 의미가 있다. 지금 채우면 좌우 중 어느 쪽 치수인지 제품이 지어내는 것이 된다.

## 읽어야 할 파일

- `CLAUDE.md` — **R13 항 전체**, ADR-012, ADR-021(카ットオフ와 切り止め位置)
- `src/lib/import/section-list/parse.ts` — 열 배정 로직. **앵커는 符号 중심이 아니라 位置 열이다**
  (phase 6에서 확정. 칸 폭이 부재마다 달라 중심 사이 중점이 실제 칸 경계와 어긋난다)
- `tests/fixtures/section-import/expected/yokohama-kanazawa-p14-girders.json` — `notes`와 `カットオフ` 항목

## 전제 — 실측한 좌표 (조사 완료, 다시 조사하지 마라)

`yokohama-p14`, `R階` 블록. ［］ 행은 **라벨이 없다** — `断面` 행보다 위에 있고 앞 칸이 비어 있다.
따라서 라벨 화이트리스트로는 잡히지 않는다. **`［` 문자 자체가 유일한 단서다.**

```
y=231.0   R階                                    ← 층 라벨
y=294.5   ［2500］ ［2700］ ［2700］ ［2700］ ［2700］ ［3000］   ← 이 행 (라벨 없음)
y=316.0   断面  650x800  650x1000 …
y=334.5   上筋  8-D25 8-D25 13-D25  9-D25 9-D25 13-D25 …
```

x 정렬 실측 — ［］는 자기 아래 **位置 열**과 맞는다 (오차 5~10pt):

| ［］ x | 값 | 같은 열의 上筋 x | 上筋 값 |
|---|---|---|---|
| 473.8 | ［2500］ | 478.8 | 13-D25 (G51 内端) |
| 591.9 | ［2700］ | 601.9 | 9-D25 |
| 828.1 | ［2700］ | 833.1 | 13-D25 |
| 946.3 | ［2700］ | 951.2 | 10-D25 |
| 1182.5 | ［2700］ | 1187.5 | 13-D25 |
| 1300.6 | ［3000］ | 1310.5 | 9-D25 |

전 픽스처에서 `［`는 **7개**다 — 위 6개 + 表題 特記의 `［］内は…` 1개.
表題의 것은 값이 아니다. 다른 픽스처(ojkk·kani)에는 `［`가 0개다.

## 작업

TDD로 진행하라.

### 1. ［］ 행 인식

- 값이 `［숫자］` 꼴인 항목만 본다. 반각 `[1500]`도 받아라 (기존 정규화가 全角↔半角을 접는 방식을 따르라).
- **表題 줄에 있는 `［］`는 제외하라** — 안이 비어 있으므로 「숫자」 조건만으로도 걸러진다.
  표제 y 범위를 하드코딩하지 마라.
- 이 행은 층 블록 안에서 `断面` 행보다 **위**에 있다. 층 블록 경계 판정을 바꾸지 마라 —
  기존 판정이 이 행을 이미 그 블록 안에 넣고 있는지 테스트로 먼저 확인하고, 안 들어오면 그때 고쳐라.

### 2. 位置 열 배정

기존 **位置 열 앵커**로 배정한다. 새 배정 규칙을 만들지 마라.
배정에 실패한 ［］는 버리지 말고 位置 없는 원문으로 남겨라.

### 3. raw에 남긴다

```
raw['カットオフ(内端)'] = '［2500］'      // 位置를 안 경우
raw['カットオフ']       = '［2500］'      // 位置를 모른 경우
```

- 후보 필드는 **만들지 마라.** `SectionCandidate`에 `cutoff` 필드를 추가하지 마라 —
  담을 모델 자리가 없는 필드를 후보에 두면 step 3의 取入이 쓸 곳을 찾다가 지어낸다.
- `CANDIDATE_ISSUES`에 새 코드를 **추가하지 마라.** issue는 「이 셀을 빈칸으로 둔 사유」인데
  カットオフ는 애초에 후보의 셀이 아니다. raw 표시가 사용자에게 가는 경로다.

### 4. 전사 픽스처의 note 갱신

`expected/yokohama-kanazawa-p14-girders.json`의 `notes` 배열 마지막 항목이 지금
「カットオフ 치수(...)는 현행 제품 스키마의 파싱 대상이 아니다 — 파서가 무시하되 죽지 않아야 한다」이다.
이 step이 그 서술을 바꾸므로 **그 한 줄만** 현재 사실로 고쳐라
(원문 보존까지 하고, 값 반영은 R13 선결이라는 취지).

**전사된 값(`entries` 이하)은 한 글자도 고치지 마라.** ADR-010 — 전사는 파서와 독립이어야 한다.

## 테스트

- `yokohama-p14` `G51`(R階) → `raw`에 `カットオフ` 계열 키가 있고 값이 `［2500］`(또는 정규화한 `[2500]`)
- 같은 후보의 `girderMain`이 여전히 빈칸이고 issue `主筋端部左右相違`가 그대로인 것
- ［］ 6개가 6개 그대로 배정되고 사라지거나 늘지 않은 것
- `ojkk-p3`·`kani-p38` 후보에는 `カットオフ` 키가 **없는** 것
- 表題의 `［］内は…`가 값으로 잡히지 않은 것

## 금지사항

- **`cutoffFromSupportFaceMm`에 값을 넣지 마라.** 이유: R13. 좌우 중 어느 쪽인지 도면이 말해도
  제품의 `Grid`·`GirderMainRow`가 그것을 담지 못한다. 지금 넣으면 제품이 방향을 지어내는 것이다.
- **「하나뿐이니 그걸 쓰자」로 분기하지 마라.** 이유: 픽스처에 그 케이스가 없다. 근거 없는 유연성은 죽은 코드다.
- **전사 JSON의 값을 고치지 마라.** 이유: ADR-010 — 전사가 파서에 맞춰 움직이면 검증이 순환이 된다.
- **열 배정 규칙을 새로 만들지 마라.** 이유: phase 6이 位置 열 앵커로 확정했고 그것이 실측 근거다.
